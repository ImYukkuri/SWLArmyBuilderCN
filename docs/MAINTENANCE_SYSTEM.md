# 资料维护系统与规则声明

更新日期：2026-11-06。本文件描述已实现的本地维护系统；公开组军产品仍以开发方向文档的首版验收为目标。

## 入口和模块边界

运行 `python server.py --port 8770`，进入 `http://127.0.0.1:8770/`。

| 模块 | 路径 | 可编辑源文件 | 历史 |
| --- | --- | --- | --- |
| 单位卡 | `/units` | `data/units.json` | `history/*.json` |
| 升级卡 | `/upgrades` | `data/upgrades.json` | `history/upgrades/*.json` |
| 军表 | `/armies` | `data/armies.json` | `history/armies/*.json` |
| 规则库 | `/rules` | `data/slot-rules.json` | `history/slot-rules/*.json` |

三个页面分别管理目录、草稿、保存和历史；切换模块不会把草稿自动写入另一个模块。
未保存离开会提示。所有模块均可编辑 JSON，固定记录 ID 不允许通过保存更换。
卡图使用项目相对路径，点击单位原图/立绘、升级原图或军表已选升级缩略图可放大。

“独立部署”指写表器具有自己的入口和发布目录，例如另一个仓库的 Pages，或同域名下 `/SWLArmyBuilderCN/`。
它不要求购买另一台服务器。现阶段此系统是本地维护服务，并未生成可直接放入上述子目录的公开客户端。
本地维护服务负责写源文件和历史，GitHub Pages 不运行 Python，也不能写回磁盘。
后续公开网站只读发布后的数据、将军表保存在浏览器/导出文件；维护服务继续独立保留。
不能把当前编辑 API 直接暴露为无认证的公网写入入口。

64 条待匹配中 63 条为 `tod-` 战役卡，已归入 `campaign`；另有一张 E-11D 翻面记录。

匹配仅使用规范化精确名称、明确宿主和脚本中的显式版本对照，不用模糊首条命中猜测。
同名 Darksaber、阵营专属装备和类似武器版本分别对齐。
翻面可共用上游 ID，`selectionGroup` 用来识别同一选项组，不能因翻面多算一张卡。
`data/upgrade-crosswalk.json` 保存匹配结果，匹配成功不代表每个字段或规则语义都已校对。

`points` 使用匹配参考版本的基础费用，旧费用差异进入 `review.issues`；原值仍在映射快照中。
运行规则层使用 `data/slot-rules.json`（`swl-rules/v1`），不是直接把上游数字当作槽位 ID。
`slots` 是语义槽位注册表（`sourceId` 只做来源追溯），`dedicatedGrants` 是专用槽授予，
`upgradeRules` 是角色限定/整军唯一/互斥组的人工语义覆盖，`modes` 是模式配额与佣兵池，
`battleForces` 是战斗部队骨架。升级卡的默认槽位匹配由卡牌自身 `slotIds` 映射到语义键；
`type:[2,16]` 表示 Gear 或 Electrobinoculars 二选一；单位重复槽则是多个独立实例。
未覆盖的复杂限制由引擎回退上游快照求值，无法判定时返回 unknown。
单位的基础槽数组保留重复项和必选标记；条件解锁槽另存，不能去重或当作永久基础槽。
词条引用统一指向 `catalog-definitions.json` 的 `keywords`；`ruleId` / `_x` 别名在加工时对齐，
规则简写和正文不在每张升级、每把武器重复保存。武器名称统一为 `{en,zh}`。
原映射和迁移快照保存了被精简的旧字段；未匹配的词条先进入待校对解释表。

`rules.py` 是语义规则引擎（纯函数），`army_preview.py` 是它的薄封装；`data/slot-rules.json`
在 `/rules` 页手工维护并保存。`import_maintenance.py` 是一次性建库器，有现有升级库时拒绝重建，避免覆盖人工修改。
后续更新要做增量差异与合并，不能通过删除现有库绕过保护。

## 规则库

规则约束集中在 `data/slot-rules.json`，由 `/rules` 页维护，不在每张卡上分散编辑：

1. 槽位注册表：26 类语义槽位（category / counterpart / dedicated）与来源 ID。
2. 专用槽授予：`dedicatedGrants` 用持有者名单或语义条件表达哪些单位获得专用槽。
3. 升级语义规则：`upgradeRules` 只覆盖需要人工语义的角色限定、整军唯一与互斥组（如 Darksaber 五个版本）。
4. 模式配额：standard/recon 的军阶 min/max、命令手牌 pips、雇佣兵池。
5. 战斗部队骨架：`battleForces` 记录母阵营、军阶配额、自然语言规则与 options 占位。

条件采用三值 `all/any/not + field/op/value`；引擎与 UI 都只读这份规则包，候选查询与整军校验共用 `rules.py`。
未覆盖字段回退冻结上游快照，无法判定时返回 unknown。

普通单位 `usage=army_unit`；伙伴卡 `usage=counterpart`，通过槽 15 由宿主选择。
伙伴声明 `countsAsActivation=false`、`costViaUpgrade=true`，保留宿主资格。
升级用途区分 `unit_upgrade`、`counterpart`、`campaign`。
军队成员关系中的 `tierCounting`、`tierPools` 等语义仍在规则包中逐步补齐，未补齐前保持 unknown。
公开产品首版依然只覆盖四大阵营 Standard 1000；维护库可保留后续主题和 Recon 资料，不等于已支持合法组军。

## 军表维护预览的真实覆盖

预览由 `rules.validate_army` 执行，已实现：单位引用、伙伴身份、军队准入、基础槽类型/占用、
必选槽、角色限定（host）、整军唯一、互斥组、必带升级（requiredChildren）、军阶 min/max/combined、
命令手牌 pips、雇佣兵池、点数上限，以及战斗部队骨架的自身军阶配额。

返回 `invalid` 表示发现明确问题；`unknown` 表示仍有待执行规则。费用修正、属性效果、
动态槽求值与战斗部队 textRules/options 仍未求值，相关项标 unknown；超过点数上限但存在
未计算的折扣时只作为明确超支提示，不武断判不合法。`effectivePoints` 当前等于基础费用，
不伪造完整费用结论。失效选择会留在军表里，不静默删除。一键清理、级联预览和撤销属于后续
公开写表器交互，当前维护工具提供逐项显式移除。

## 保存与验证

### 2026-11-13 编辑交互更新

单位、升级、战术卡、军表及规则库共用 `editor-shell.js` 与 `editor.css`。
保存、新建、重载等全局操作固定在顶部，工具栏高度变化会自动调整内容偏移；
`Ctrl/Cmd+S` 调用原有保存流程，冲突处理与文件历史继续使用现有 API。

单位属性和单位/升级武器通过 `editor-forms.js` 共用表单。
属性支持空值、零值、破折号与 X，防御骰及激增转换以图标选择；
武器显示近战、远程或兼用射程提示，以及三色骰池。
升级武器的可变骰数 X 仍按原结构保存为 `-1`。

`editor-options.js` 在单位/升级编辑器进入时并行加载五份已有数据：
目录定义、单位、升级、槽位规则及规则字段定义，并缓存同一次加载结果。
它分别索引本地 ID、来源 ID、语义槽位和数字枚举，供规则表单和表达式共用。
下拉支持中英名称/ID 搜索；嵌套条件值随所选字段切换，集合条件逐项编辑。
不识别的现有引用会明确保留，需要自由表达的字段可手动输入；
仅展示不会改写源数据，界面索引不会进入导出的 JSON。
重新载入会重新取得目录，避免继续使用旧选项。

本次逐一对照原卡图检查单位和升级武器中原射程为 `1–1` 或 `2–2` 的记录：
单位共 19 条，升级共 0 条。18 条兼用武器的最小射程修正为 0；
B2 的 Wrist Rockets（腕部火箭）为纯远程，保留 `1–1`。
`weapon_range.py` 使用原有红/蓝射程区识别结果辅助 OCR，
避免单独识别到上限数字时丢掉近战资格；原最大射程及其他字段不变。

服务仅绑定本机；固定文件路径、同源 JSON 请求、结构校验、SHA256 版本冲突和原子写入。
每次成功保存/恢复/删除先备份，冲突返回 409，保留当前浏览器草稿。
历史恢复只替换当前记录；删除军表的完整旧文件同样有备份，API 支持从快照重新恢复该 ID。
界面历史按钮用于恢复当前选中的记录，不提供整个文件回滚。

验证命令：`npm test`，以及四份编辑脚本的 `node --check`。
实际浏览器已验证限制保存/恢复、原图放大、三个入口、军表保存/恢复/删除、390px 布局。

## 发布边界

本项目位于原转换器仓库旁，未自动提交或部署。
卡图已经接入本地网站；用户要求的公开展示意图已记录，但上游数据和素材的公开分发方案仍待落实。
完整卡库、卡图、OCR、参考快照和历史不得复制到原公开转换器仓库，原仓库的发布审核不变。
维护代码与公开客户端可以分开发布；不能把整个私有维护目录当作 Pages 上传目录。
