# 任务：0.18.0 规则引擎升级卡候选查询性能优化

请直接在当前项目工作区实施第一轮性能优化，不要只输出分析报告或实施计划。

## 一、任务背景与性能基线

当前版本：0.18.0\
基准提交：`b1a4af5`

本机已经复现的性能问题：

| 场景 | 打开升级卡槽位 | 装备后切换下一槽位 |
|---|---:|---:|
| 共和国基础规则 | 168 ms | 124 ms |
| 自定义克隆人营 | 753 ms | 895 ms |

测试军表：12 个单位，43 张训练升级卡候选。

主要目标不是优化页面加载、JSON 下载或数据分包，而是直接降低：

1. 打开一个升级卡槽位时，计算 43 张候选卡合法性的耗时。
2. 装备一张卡后，计算下一槽位 43 张候选卡的耗时。
3. 用户点击升级卡时，重复执行的装备模拟和完整规则校验。

目标是在不改变任何规则结果的前提下，显著降低自定义克隆人营的候选查询耗时。

## 四、第一项优化：消除点击时的重复装备模拟

当前 `builder.js` 的 `choose(card)` 存在重复工作：

1. 清空 `stateCache`。
2. 调用 `computeItemState(card)`。
3. 对升级卡而言，`computeItemState()` 内部已经调用 `prepareUpgrade(card)`。
4. 后面升级卡分支又调用一次 `prepareUpgrade(card)`。

这导致同一次点击执行两遍完整装备模拟。

请直接修复：

- 对 `browser.mode === "upgrades"`，点击时直接执行一次 `prepareUpgrade(card)`。
- 以这一次返回的结果作为本次正式装备的权威结果。
- `result.ok === false` 时显示原有失败原因，不改变军表。
- `result.ok === true` 时使用 `result.draft` 提交并执行原有切槽流程。
- 其他单位和战术卡的选择流程保持原样。

不能直接信任旧的 `stateCache` 结果。点击时仍必须重新进行一次正式规则确认，只是不能重复确认两遍。

## 五、第二项优化：共享装备前的基准校验报告

这是本轮必须实现的优化。

当前 `BuilderModel.newErrors(before, after, data)` 每次都会执行：

`RulesCore.validateArmy(before, data)`\
`RulesCore.validateArmy(after, data)`

在一次候选列表计算中，43 张卡的装备前军表基本相同。

因此当前可能进行：

- 43 次装备前完整校验。
- 43 次装备后完整校验。

装备前的校验报告应该只计算一次，43 张候选卡共享这一份报告。

### 建议实现方向

给 BuilderModel 增加一个轻量、生命周期明确的候选校验上下文。

例如：

`BuilderModel.createEquipPreviewContext(army, data)`

内部保存：

- 基准 army 引用。
- 对应的数据源和规则配置身份。
- 装备前的完整 `validateArmy()` 报告。
- 必要的上下文版本信息。

给 `BuilderModel.equip()` 增加可选的预览上下文参数，并允许 `newErrors()` 接收已经计算好的 `beforeReport`。

伪逻辑：

```js
function newErrors(before, after, data, beforeReport = null) {
  const baseline =
    beforeReport || RulesCore.validateArmy(before, data);

  const afterReport = RulesCore.validateArmy(after, data);

  // 保留原有错误差异比较、数量比较和过渡性规则处理
}
```

以上仅为接口示意，实际实现要符合现有代码结构。

### 严格要求

1. 共享的是同一份基准军表的校验报告，不是装备后的结果。
2. 每张候选卡仍然必须执行装备后的完整规则校验。
3. 不能因为命中缓存而跳过唯一性、互斥、Equip 或特殊槽位检查。
4. 上下文只能用于完全匹配的基准军表和数据源。
5. 军表、战斗部队选择、规则组或数据源发生变化时必须失效。
6. 槽位切换、批量装备开关和重新打开候选列表时，要确保上下文不会引用错误状态。
7. 上下文不存在、已失效或无法确定适用范围时，回退到现有完整校验路径。
8. 不得为了判断上下文是否有效，在每次候选卡计算时重新执行昂贵的完整军表序列化。

可以将这个上下文限定在一次候选列表会话中，避免设计复杂的长期缓存系统。

搜索框和排序变化不改变军表，可以继续复用候选状态和校验上下文。

**这个优化必须先完成并测试，再继续处理 V2 内部缓存。**

## 六、第三项优化：将 V2 静态派生数据与动态装备状态分离

这是本轮最重要的结构性优化。

当前 `BattleForceRuntime.resolve()`：

- 以 `JSON.stringify(army)` 作为动态缓存键。
- 每个不同的候选装备状态都可能产生一次缓存未命中。
- 缓存最多保留 8 个完整军表状态。
- 每次未命中都会重新遍历 `source.upgrades` 和 `source.units`。
- 重新克隆大量卡牌。
- 重新应用 Battle Force modifiers。
- 重新执行 UpgradeFaces.index。
- 重新建立 nameIndex。

43 张候选卡意味着不同的装备状态会大量冲击这个缓存。

### 核心设计

不要继续以「整个军表状态」作为所有派生数据的缓存单位。

拆成两层：

**A. 规则集静态编译结果**

在规则组和 Battle Force 选择保持不变时，可复用：

- 生效的 common 和 ruleGroup scopes。
- modifiers。
- entries。
- unitGrants、upgradeGrants。
- uniqueUpgradeIds。
- 全局升级卡派生目录。
- 不依赖具体装备状态的基础单位派生目录。
- 对应的 UpgradeFaces 索引。
- 基于派生升级卡构建的 nameIndex。
- 规则组相关的静态配置。

缓存键至少需要包含：

- 原始 source 对象身份。
- armyId。
- 当前有效 ruleGroup IDs 或等价的规则选择签名。

不能只按 armyId 缓存，因为同一战斗部队可以选择不同规则组。

**B. 军表动态实例结果**

每次不同装备状态变化时，只重新计算真正依赖实例状态的内容：

- `pkg._v2.instances`。
- 每个实际单位实例的有效状态。
- 当前 rankId。
- `when.equippedSlot` 条件效果。
- 由当前已装备卡决定的条件性关键词、槽位及其他效果。
- 与当前实例有关的诊断 issues。

已经确认的关键区别：

`makeUnit(raw)` 和 `makeUnit(raw, inst)` 不能简单地合并成一种缓存。

前者的基础派生结果在相同规则集下可以共享；后者会根据具体实例的 rank 和 equippedSlot 重新计算。

### 必须保持的规则语义

- 不同实例不能错误共享动态状态。
- 装备前后的条件性效果必须正确变化。
- 规则组切换后必须使用新编译结果。
- 未启用或定义无效的 Battle Force 保持原有诊断路径。
- `data.units` 和 `data.upgrades` 的源卡不能被原地修改。
- `pkg._v2.instances`、动态 issues 不能被静态缓存污染。
- 不允许把候选卡引起的条件性变化误当成静态效果。
- 不允许因为缓存而遗漏 `_v2Allowed`、`_v2Ranks`、`_v2ArmyGrant` 等字段的正确状态。

可以复用现有 `resolve()` API，不要求 UI 或 RulesCore 知道内部缓存结构发生变化。

如果实现静态派生缓存时需要调整 `makeUnit()`，请明确分离静态 modifier 和动态 modifier，不要简单地缓存整个 `makeUnit()` 结果。

缓存对象必须视为只读。需要修改时采用局部复制，避免候选试算之间互相污染。

如果这一项的正确性不能在本轮得到充分验证，先保留原有 resolve 路径，并提交前两项已经验证的优化，不要冒险合入不完整缓存。

## 七、顺手检查 RulesCore 中的重复工作

重点检查 `rules-core.js` 的 `validateArmy()`。

当前每次校验都可能：

- 规范化整个 army。
- 克隆军表。
- 对升级卡重新建立 UpgradeFaces 索引。
- 重新构建 nameIndex。
- 在校验循环中反复调用 `unitFor()`，而 `unitFor()` 又会进入 `resolveArmyData()`。

请分析这些操作的实际必要性。

允许优化：

- 对同一份不可变派生升级卡目录复用 UpgradeFaces 索引。
- 当 `data.nameIndex` 确实对应当前升级卡目录和 defs 时，复用现有索引。
- 同一次 `validateArmy()` 中已经解析过的 runtime data 可以直接使用，不要对每个单位重复执行完整的 resolve 入口。
- 避免无意义的重复遍历和重复创建临时对象。

但需要特别谨慎：

`UpgradeFaces.normalizeArmy()` 在 V2 生效前和派生数据生成后出现两次，可能承担不同的规范化职责。不要只因为看起来重复就直接删除其中一次。先确认两个阶段的输入、输出和规则要求，再决定是否可合并。

所有优化必须有测试证明新旧行为一致。

## 八、暂时不要做的优化

暂时不要实施：

- 全军增量规则校验的全面重写。
- 独立的简化合法性判定器。
- 大规模的 RulesCore 拆分。
- 所有候选合法状态的长期缓存。
- 复杂的 Proxy、异步规则加载或 Worker 化。

如果发现 `selectionFailure()` 中全军升级统计和 `unavailableSets()` 重复计算占据显著耗时，可以在分析报告中提出下一步局部优化建议，但本轮优先完成上面三项。

重点覆盖：

10. 通过装备替换释放互斥和唯一性限制。
11. 双面卡、正反面切换。
12. `applyAll` 批量装备。
13. 同名单位合并组。
14. 不完整军表和既有错误的差异比较。
15. 不同规则组切换、撤销选择和重新装备。

增加测试，验证：

- 同一个候选计算上下文下多张卡共享基准校验报告。
- 装备后报告仍然针对各自不同的候选军表重新计算。
- 上下文失效时正确回退。
- 新旧装备模拟结果一致。
- 静态 V2 派生数据不会因候选模拟而改变。
- 不同装备状态下实例级条件效果正确。
- 原始 source 数据保持不变。

对于相同输入，尽量使用固定 ID 生成器，比较新旧路径的 `ok`、`reason`、`warnings`、装备目标、槽位和最终 draft。不能只比较是否允许装备。
