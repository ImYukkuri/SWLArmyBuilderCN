### 缓存边界

- 预览 token 只在一次同步候选计算中有效，微任务到达即失效；正式点击从不传 token。保存军表引用及快照，逐项比对而不执行完整 JSON 序列化。源、目录、规则配置引用变化或军表内容变化都回退完整校验。销毁／重开面板也会主动丢弃 token。
- 同步计算期间目录作为只读输入。维护页正常重载会提供新的源对象。若其他调用方主动原地修改已有 V2 目录，必须先调用 `BattleForceRuntime.invalidate(data)`；仅修改卡牌内部属性却不通知运行时不属于缓存契约。
- V2 静态缓存最多 8 个规则集。重载源目录、替换部队表／定义／V2 配置／模式对象会清理缓存；实例状态变化只重建实例。
- 静态单位、升级卡（含反面别名）、局部规则、效果及当前部队派生定义深度冻结；不会冻结或修改原始 source。实例及 issues 每个动态快照各有一份，不写回静态目录。
- 为保持语义，实例从身份／基础军阶派生模板开始，其他效果在确定实例军阶后一起执行。不能先应用静态“设为”，再单独叠加条件“设为”，否则会改变冲突判断。本轮保留原有整体排序及冲突规则。
- nameIndex 属于只读查询索引，必须与创建它的升级目录、defs 和 defs.upgrades 数组一致；无法确认时重建。没有删除两次双面卡规范化。

## B. 性能数据

环境：Windows、Chrome 158.0.8127.36、Node 24.20.0；390 × 844 手机视口，未模拟移动设备 CPU 限速。每个场景独立浏览器上下文运行 5 次，取中位数。计时为实际 DOM 点击到同步处理结束；另记录两个动画帧后的时间。旧版／新版使用同一数据、服务和计时包装，顺序运行，没有同时执行其他测试。

固定军表：绝地武士将军、4 个克隆人士兵部队、2 个克隆人突击队、2 个 BARC、Saber、克隆人指挥官、绝地武士，共 12 个单位。将军的训练槽有 43 个候选；选 Endurance 后继续下一训练槽。克隆人营选择突击／果决／加强编制。

“冷”在点击前更换源对象身份，同时清空新旧引擎的两层缓存，保留相同页面和卡牌数据，计入一次静态编译。“热”在同一页面重复交互；原来的 8 项动态缓存仍会淘汰候选状态，不能假定热查询全部命中。下载及页面初始化不计入点击耗时。

## D. 本轮实测后仍值得关注的工作

1. **保留的完整装备后校验**：共和国热查询约 44–45 ms，V2 约 23 ms。下一轮可进一步分析校验内部哪些只读统计重复创建；仍保留最终完整校验，不另建简化判定器。
2. **动态实例和重复 resolve 入口**：V2 热查询仍有 1028–1064 次入口，累计约 16–17 ms，其中实例构建约 12 ms。可继续局部传递一次操作内已解析的数据，但必须按军表状态区分，不能把候选前的数据用于候选后。
3. **普通目录的 nameIndex 构建**：共和国热查询仍建 22–23 次，约 11 ms。它目前可变，故本轮未冒险复用；后续如建立明确的目录修订标识，可单独优化。

未量到 `selectionFailure`／`unavailableSets` 的独立耗时，因此不将它们直接认定为下一轮瓶颈。没有扩展到数据分包、Worker 或全军增量校验。
