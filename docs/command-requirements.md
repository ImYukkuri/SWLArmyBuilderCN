# 指挥卡使用条件

指挥卡的 `requirements` 是当前使用资格的唯一数据来源。单位中的旧 `commandIds` 仅为历史导入资料，不参与资格判断；`owner` 只负责显示卡面归属。

```json
{
  "requirements": {
    "any": [{
      "all": [{
        "type": "unit",
        "all": [
          {"field": "nameIdentityId", "values": ["obi-wan-kenobi"]},
          {"field": "title", "values": ["Mounted Jedi General"]}
        ]
      }]
    }]
  }
}
```

`any` 中任一条件组成立即可；组内 `all` 条件必须全部满足。`{"any":[]}` 明确表示不限；空条件组或空匹配值属于未完成配置，禁止保存和选择。

| type | 匹配范围 | 取值 |
| --- | --- | --- |
| unit | 军表中的同一单位，同时满足其 all 筛选 | id、name、title、nameIdentityId、factionId、affiliationIds、rankId、unitTypeId、keywords |
| unitNames | 每个名称都存在，分别由不同单位实例满足 | 英文单位名称数组，至少两个 |
| armyFaction | 军表所属势力，战斗部队递归取母势力 | 本地军队 ID；曼达洛 8、暗影集会 9 |
| battleForce | 精确匹配选中的战斗部队 | 本地战斗部队 ID |
| upgrade | 军表已装备其中任一升级 | 本地升级卡 ID |

普通筛选的多个 `values` 为“或”。名称和称号执行 NFKC、空白、大小写标准化后的精确比较；不使用模糊包含、不拆分组合角色名。下拉展示中英双语，名称／称号保存英文值；名称标识保存稳定的 `nameIdentityId`。改译名不影响英文匹配，改英文名或称号应同步检查依赖条件。单位 ID 改名操作会自动更新具体单位绑定。

军表组织读取战斗部队结算后的单位实例，再叠加已装备升级的属性变更。伙伴升级本身不冒充独立单位；需要伙伴的条件使用已装备升级匹配。

`RulesCore.commandContext` 每次查询建立一次索引，全部候选复用；`commandEligibility` 同时供选择器和军表校验使用。每次查询重新读取军表，点击选择时再次检查。V1 的 Python 预览使用 `command_requirements.py`；V2 通过现有 JS bridge 执行同一套运行时。

卡面点数 `pips` 保留游戏中的优先级；手牌分配和数量校验统一读取 `slotPips ?? pips`（`RulesCore.commandSlotPips`）。例如袖中王牌印刷 1 点、组军占 2 点。TTS 导入使用组军点数定位；原生导入和打开旧军表时，`BuilderLibrary.normalizeCommandSlots` 保留已正确放置的卡，将错位或原先追加在末尾的卡移入对应空槽。真正超额、重复和引用缺失的卡均保留并在主界面显示，可手动删除，不再因超出固定七个位置而隐藏。

编辑器的使用条件组件复用 `EditorOptions.control` 与可搜索下拉，打开页面时从当前 JSON 提取名称、称号、名称标识、单位、阵营、组织和战斗部队选项。“刷新候选项”重新加载词典并保留当前草稿。旧历史快照仍可按原有字段校验；编辑旧记录时需要配置新的使用条件。

编辑入口：本地 `commands.html` → 选择指挥卡 → 字段编辑 → 使用条件。

- “添加备选条件组”：满足任意一组即可使用。
- 组内“添加条件”：各条件必须同时成立，允许由不同单位满足。
- “叠加同单位条件”：名称标识、称号、组织等条件必须由同一个单位满足。
- 每项下拉可搜索并添加多个候选值；普通匹配任选其一，名称组合则必须全部在场。
- 删除全部条件组表示通用；保留空条件行会阻止保存，避免未配置完整的限制被当作不限。

验证覆盖全部可用指挥卡的引用、前后端匹配、保存与历史恢复、单位 ID 修改、224 和伍基人林地战团，以及手机／桌面的实际选择、删除条件和候选刷新。10 单位、235 张候选的整批条件查询（含说明文字）在开发机约 3 毫秒；此数值不含 DOM 和图片渲染，也不代表手机耗时。
